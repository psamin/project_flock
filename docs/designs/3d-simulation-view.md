## Problem Statement

The current Canvas 2D renderer reads as a video game, not as a robotics
simulation. That undercuts the pitch: Colony claims to be a coordination layer
for heterogeneous robot fleets in high-stakes environments (PRD §2.5), and a
top-down pixel-art view invites a judge to read it as a toy. The fix is a
second, toggleable view at `/sim3d` that presents the same mission as a
floating-island digital twin — orbitable, instrumented, with robots that
visibly perceive and act.

The 2D view at `/` is not modified and remains live.

## What Makes This Cool

A city block that **builds itself out of the dark** as the fleet explores, and
then stays dimly lit where nobody is currently looking. That single visual is
the entire thesis of the project — "remembered but not currently observed" is a
state that only exists because the fleet writes to shared memory — and it is
dramatically more legible as a 3D lighting effect than as the 32% alpha
rectangle it is today.

Second: robots that read as machines. A scout with a swept sensor volume and an
altitude shadow, a lifter whose arm extends into the debris it is clearing, pose
telemetry with decimals and units. The claim "physical intelligence" stops being
a word in the writeup and becomes something a viewer watches happen.

## Premises

1. **The simulation does not change.** `/sim3d` is a new view over the same
   authoritative sim. No server logic changes, no continuous physics. "Physical
   intelligence" is expressed in the view — interpolated pose and heading, sensor
   volumes, articulated action animation — over discrete truth. This is what
   makes the change safe two days out.
2. **Everything needed is already on the wire.** `World.snapshot()`
   (`colony/sim/world.py:599`) ships `ground`, `objects`, `zones`, `sectors`,
   `shared_vision`, `seed`, `mission_length_ticks`; per-robot frames carry
   `role`, `status`, `facing`, `vision`, `bubble`, `x`, `y`. The protocol in
   `colony/sim/protocol.py` is unchanged.
3. **Geometry is procedural.** Buildings, robots, and the slab are built in code
   from tile and zone data — the same argument that produced `atlas.js`: a repo
   that needs an asset fetch before it renders is a repo that breaks on someone
   else's laptop the day before the deadline.
4. **WebGL becomes a hard requirement for `/sim3d` only.** This reverses the
   decision documented at the top of `app.js`, where PixiJS was rejected because
   it renders nothing at all without WebGL. The reversal is defensible only
   because `/` keeps working — so `/` keeps working.
5. **`atlas.js` is not modified; `app.js` changes by import lines only.**
   *(Amended by eng review, decision 4A.)* The renderer-independent code —
   `TICKER_TEXT`, `TICKER_CLASS`, `setText`, `updateHud`, a new pure
   `formatEvent(e) → {text, className}`, and the commander console block — is
   extracted into `ui-shared.js` and imported by both routes. Copying it would
   mean HUD and ticker fixes must be applied twice during the two days those are
   tuned most, and the two views showing different numbers for one mission is a
   worse failure than the extraction risk. `connect()` stays duplicated: it calls
   `boot()` and `applyTileChanges()` and is genuinely renderer-coupled.
   `logEvents` also stays per-renderer — `app.js:544` and `app.js:546` mutate
   `shakeUntil` and `ghosts`, which are renderer state.

   The extraction touches the recording fallback, so verifying that `/` still
   renders and its HUD populates is a **blocking gate** (task T5), not a
   nice-to-have.
6. **The Stage One beat is satisfied on `/sim3d`.** The three-state fog is the
   memory layer at work, and the commander console DOM ports over unchanged so
   live SQL still appears on screen.

## Approaches Considered

### Approach A: Environment-first digital twin

The island is the hero — zone-styled masses, materials, sun and soft shadows,
bloom, dust haze. Robots stay simple meshes with cones. Lowest risk, closest to
the reference image, best wide shots. **Rejected:** leaves the robots as the
least convincing thing on screen, which is the exact complaint that started this.

### Approach B: Agent-first robotics rig

All budget into robot rigs — interpolated yaw, swept occluded sensor frusta,
articulated lifter arm, medic deploy, scout rotors, path traces, telemetry.
Environment stays flat-shaded. Strongest on the stated complaint. **Rejected:**
wide establishing shots look unfinished, and a judge's first frame is a wide shot.

### Approach C: Screen-time-weighted, with a camera director — CHOSEN

Split the budget by how long each thing is actually on camera. Environment gets
breadth, robots get depth, plus a camera director driven by the existing events
stream.

### Also considered and rejected earlier in the session

- **Pixel-art isometric diorama** matching the reference image literally.
  Rejected because pixel art is the most video-game-coded aesthetic available,
  and the presenting complaint was that the view looks like a video game.
- **Pixel diorama with a telemetry overlay.** Rejected as the hybrid trap —
  PRD §3.6's own style test fails anything that reads as an engineering debug
  view bolted onto a game.
- **Making the simulation itself continuous.** Rejected: breaks determinism, the
  test suite, and the audit findings, for a perceptual gain the view layer can
  deliver on its own.

## Recommended Approach

**Approach C.** The reasoning that decided it, which cuts against the obvious
advice: the instinct is to polish what the reference image emphasises, and that
image is almost entirely environment. But the reference is a *still*, and this
is a three-minute video where 3D carries every beat. **Screen time, not
reference-image emphasis, sets the budget.** A wide establishing shot is on
screen for two seconds and only needs to read at a distance. The robots are on
screen for all 180 seconds and get looked at closely — they are what a viewer is
actually watching when they decide whether this is a simulation or a game.

The camera director is the least obvious piece and the one worth defending. The
`events` stream already carries `task_claimed`, `victim_stabilized`,
`debris_cleared`, `aftershock`, and `robot_lost` (see the `TICKER_TEXT`
vocabulary at `colony/client/app.js:510`). Wiring those to camera moves means
the footage frames itself, which turns "record a 1200-tick mission and hope the
camera was pointed the right way" into something shootable in one take. With
under 48 hours left, the recording problem is as real as the rendering problem.

### Tile and zone mapping

Ground and object types come straight from the snapshot grids:

| Tile | Geometry |
|---|---|
| `open` | slab tile, height 0.1 |
| `wall` | extruded mass, height set by zone (below) |
| `door` | wall mass with a cut opening and a lintel |
| `unstable` | slab at 0.1 with a cracked, faintly emissive material |
| `debris` | scattered low boxes, ~0.6 |
| `rubble_heavy` | denser boxes, ~1.0 |
| `fire` | emissive quad + point light, animated on the existing 3-frame cadence |

Zones (`world.zones`, already on the wire) drive the building masses and are
what turns a tile grid into a place that reads as a city:

| Zone | Extent | Treatment |
|---|---|---|
| `staging` | 10×8 at (0,0) | low flat structures, containers, tarps, base lighting |
| `street` | 40×6 at (0,8) | road surface, lane markings, kerbs |
| `residential` | 22×16 at (0,14) | narrow 2–4 storey masses, warm materials |
| `office` | 16×16 at (24,14) | tall 6–12 storey masses, cool glass |
| `courtyard` | 2×16 at (22,14) | open, planters, connects the two blocks |

Contiguous `wall` regions within a zone extrude to that zone's height band, which
is what produces distinguishable buildings rather than a uniform slab of cubes.

### Three-state fog as lighting

Implemented as per-instance tint on `InstancedMesh`, one mesh per
geometry/material family:

- **unseen** — instance matrix scaled to 0. The tile is not merely dark, it is
  absent, so the city visibly builds itself as the fleet explores.
- **remembered** (in `explored`, not in the current visible set) — instance tint
  darkened and desaturated, no specular contribution.
- **observed now** — full tint, lit.

In `PRIVATE MAPS` (coordination OFF) mode the remembered tint goes dimmer still,
mirroring `BASELINE_STALE_ALPHA` in `app.js:37`, so the ON/OFF comparison reads
in 3D exactly as it does in 2D.

### Robot rigs and sensor volumes

Pose comes from the existing tween state (`motion`, `app.js:119`) plus
interpolated yaw from `r.facing`. Within each 250 ms tick window, spend roughly
the first third rotating and the remainder translating — turn-then-move is the
single cheapest cue that separates a machine from a game sprite.

- **Scout** — hovering body, spinning rotor disc, altitude ~1.2 with a soft
  ground shadow, downward sensor volume.
- **Lifter** — tracked base, articulated arm that extends toward the target tile
  while `status` is acting on `clear_debris`, retracting on `debris_cleared`.
- **Medic** — wheeled cart, stretcher deploy animation on `victim_stabilized`.

**Consistency requirement, and the bug to avoid:** derive the sensor volume from
the *same footprint the fog uses* — the set computed by `visibleNow()`
(`app.js:138`), which is a square of radius `r.vision`, not a line-of-sight cone.
If the cone is drawn as an idealised occluded frustum while the fog still lights
a square, the two will visibly disagree and a viewer will see a robot "seeing"
tiles that stay dark. Either extrude the actual visible set, or change both
together — never one.

### Camera director

Cues bind to the existing event vocabulary at `app.js:510`:

| Event | Camera |
|---|---|
| `task_claimed` | dolly to the claiming robot, medium framing |
| `victim_found` | quick push toward the sighting |
| `victim_stabilized` | snap to the medic, hold two beats |
| `debris_cleared` | stay on the lifter through the arm retract |
| `aftershock` | pull wide, shake, hold the whole island |
| `robot_lost` | slow drift toward the silent robot |
| idle > 4 s | slow orbit at establishing distance |

Manual orbit is always available; the director is a toggle, off by default when a
human is driving and on for recording.

## Open Questions

- **Three.js version and vendoring shape.** Pin a specific release, commit the
  module files, and add the MIT notice to `ASSETS.md` alongside the existing
  art-provenance entries. Not yet decided which release.
- **Building extrusion fidelity.** Contiguous-region extrusion per zone is
  specified above, but the actual `wall` layout in `aftershock.json` may produce
  masses that read as blocks rather than buildings. Worth eyeballing after step 1
  and adjusting height bands before investing in materials.
- **Recording machine GPU headroom.** 1,200 instanced tiles plus a handful of
  rigs is light, but bloom and shadow maps are where frame time goes. Decide the
  post-processing budget on the actual recording machine, not in development.
- **Does the legend still work?** The three fog states are explained in
  `index.html`'s legend with colour swatches. Those swatches are 2D alphas; the
  3D equivalents need their own legend treatment or the "remembered" state loses
  its label — and that label is the thesis.

## Success Criteria

1. `/sim3d` renders the Aftershock mission with orbit, pan, and zoom, while `/`
   continues to serve the unmodified 2D view.
2. The three fog states are visually distinct at video resolution, and the
   "remembered" state is identifiable without narration.
3. Clicking a robot opens the existing provenance panel with its Bedrock plan
   rationale and `plans.based_on` sources (FR-17).
4. Robots show pose, heading, sensor footprint, and per-robot telemetry; the
   lifter's arm visibly participates in `clear_debris`.
5. The commander console answers all six questions from `/sim3d`, with SQL
   on screen.
6. A full mission can be recorded in one take with the director enabled.
7. Every video beat has a 2D fallback shot that works if 3D is not ready.

### Deviations from the plan, and why

- **No decorative city.** The plan assumed zones could drive a dense block. They
  cannot: the map is 1,009 open tiles against 178 walls, and those walls are the
  boundary rectangle plus the office rooms. Massing drawn on the playable
  surface would misrepresent where robots can go, so the scene renders the
  disaster site the data actually describes. A surrounding skyline was built and
  removed — the camera orbits from 6 to 90 units, so any ring close enough to
  read puts the camera inside it.
- **The map border is not a building.** Extruding the outer ring to zone height
  built a 6-13 unit rampart that hid the whole mission from every angle. Border
  tiles render as a 0.7 retaining wall.
- **Height is per building, not per tile.** Hashing each tile independently
  turned the office into a forest of mismatched pillars. Heights now come from a
  coarse 6×6 block hash so contiguous walls share a storey and read as one mass.
- **Fog mix cut from 0.72 to 0.44.** "Remembered" is the steady state — coverage
  reaches 100% and little is under a sensor at any instant — so an aggressive
  mix turned the entire block near-black. Live tiles are lifted 1.16× instead.
- **Labels are compact by default**, expanding only for the selected robot. Four
  full telemetry blocks covered the diorama they annotated.
- **`window.__colony`** — a read-only QA surface. A WebGL canvas is opaque to the
  DOM, so the smoke check needs the renderer to report its own state.
